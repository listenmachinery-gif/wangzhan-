# ZYRON CMS P0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a production-capable, database-backed ZYRON CMS to the existing Next.js application while preserving all current public URLs and standardizing every product detail page on the Small Electric Shearing Machine module layout.

**Architecture:** The existing Next.js application remains the only deployable application. PostgreSQL/Prisma becomes the source of truth behind server-only repositories and services; `/admin` provides authenticated Chinese management UI, while compatibility adapters feed published records into the existing public routes and the standardized product renderer. Object storage, SMTP notification, cache revalidation, and audit logging sit behind explicit service interfaces so tests use real application behavior with isolated infrastructure.

**Tech Stack:** Next.js 15.5, React 19, TypeScript, Tailwind CSS 3, PostgreSQL, Prisma, Zod, Argon2id password hashing, opaque database sessions, S3-compatible object storage, Vitest, Testing Library, Playwright, and existing Nodemailer.

**Spec:** `docs/superpowers/specs/2026-11-14-zyron-cms-p0-design.md`

## Global Constraints

- Preserve every current public route, slug, legacy redirect, layout contract, image reference, and search-engine signal.
- Do not rebuild or broadly restyle the public site.
- Existing imported product slugs are immutable in P0.
- Every product detail page uses the Small Electric Shearing Machine module catalogue; unavailable content is hidden, never invented.
- PostgreSQL is the authoritative mutable store; permanent dual writes to TypeScript files are forbidden.
- Persist valid inquiries before attempting email notification.
- All authorization is enforced on the server; hidden UI is not a security boundary.
- Never commit secrets, uploaded binary files, or a default production administrator password.
- Do not modify, stage, or commit the pre-existing changes in `data/small-electric-shear-page.ts`, `scripts/verify-small-electric-shear-page.mjs`, or the three untracked `public/products/shearing/small-electric/hero/*-v2.jpg` files unless a later task explicitly needs and isolates them with user approval.
- No production deployment, production database migration/import, object-storage provisioning, or production administrator bootstrap without separate explicit authorization.
- Each task follows RED → GREEN → REFACTOR and ends with targeted tests, the full test suite, TypeScript, ESLint, and production build before commit.

## Review Focus

- A stale admin form must receive a conflict response instead of overwriting a newer edit; Task 7 adds the integration and route tests.
- A Sales user must never read, export, or update an unassigned lead; Task 10 adds row-level authorization tests.
- An SMTP or object-storage failure must not create inconsistent database state or lose a valid lead; Tasks 4 and 10 add transaction/failure tests.
- A migration with ambiguous or missing legacy content must report it without inventing or silently dropping content; Tasks 5 and 6 add importer and parity tests.
- Publishing must not expose draft/archived content, stale metadata, or changed URLs; Tasks 6, 9, and 11 add public repository, revalidation, and URL/metadata tests.
